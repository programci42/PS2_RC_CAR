PS2 USB Relay Project

This document explains what the project in this repository does, how it is structured, and — in its simplest form — how data is sent from a PlayStation 2 to a USB device. The goal is not to memorise every line of code, but to answer why each piece exists.

1. The project in one sentence

A homebrew application that drives a Seda Elektronik 8-channel HID relay board plugged into the PlayStation 2's USB port, using the DualShock controller. Hold a button and the relay closes; release it and the relay opens.

The vehicle has four RS-540 motors: the two left motors are wired in parallel as one group, the two right motors as another. Relays 1–2 drive the two terminals of the left group, relays 3–4 the two terminals of the right group.

ButtonMotionON relaysOFF commands
Cross (X)Forward1 + 317 + 19
SquareTank turn left2 + 318 + 19
TriangleReverse2 + 418 + 20
CircleTank turn right1 + 417 + 20
Controller unplugged / restart17, 18, 19, 20 = switch every relay off individually

The board is identified by VID 0x178E / PID 0x07D9. These values can be changed from inside the program (settings screen) and are saved to the memory card.

2. Four layers — who does what

Driving a USB device on the PS2 is not a single-file job, because the console contains two separate processors and the USB hardware is attached to only one of them. That is the sole reason for the project's odd-looking split.

EE — Emotion Engine main.c

The main CPU (MIPS R5900, 300 MHz). Your "application" runs here: printing to the screen, reading the controller, menus, memory card, the password screen. It cannot access the USB hardware directly.

IOP — I/O Processor iop/seda_relay_irx.c

The helper CPU (MIPS R3000, 36 MHz — in fact the PS1's CPU). All peripherals — USB, memory card, disc drive, audio — hang off this chip. This is the side that physically sends the USB packet. Modules that run on the IOP have the .irx extension.

usbd.irx Sony's stock module

Sony's USB host stack. When a device is plugged in it enumerates it, reads the descriptors and exposes the sceUsbd* functions. You do not write this; you take it from PS2SDK and embed it inside the ELF.

Relay board hardware

Appears as a USB HID device. Its microcontroller looks at the incoming one-byte command and closes or opens the matching relay. The relays keep their state inside the board (latched).

Why are the IRX modules embedded in the ELF? So the program can run from a disc or a USB stick. If the .irx files were kept separately, the program would have the "where on disk do I find them?" problem. The bin2c tool turns an IRX file into a C array (unsigned char usbd_irx[] = {...}) and the program loads it from memory. One file, zero dependencies.

3. What happens when you press a button

The path from pressing Cross to the relay going "click":

[1] padRead() EE read controller state | [2] pressed_buttons & PAD_CROSS EE "newly pressed" detection | [3] relay_set(0, 1) EE relay 0, state ON | command = 1 is chosen [4] SifCallRpc(...) EE ---> send the call to the IOP | (SIF hardware bridge) [5] rpc_handler() IOP call is received | [6] seda_send_command(1, mode) IOP 8-byte report is prepared | byte[0]=0x01, byte[3]=0x01 [7] sceUsbdInterruptTransfer() IOP ---> usbd.irx | [8] USB interrupt OUT packet USB ---> over the cable to the board's | interrupt endpoint [9] board decodes the command HW relay 1 closes | [10] transfer_done() callback IOP result comes back | [11] SifCallRpc returns EE result/status printed on screen

When the button is released the same path is repeated with command 17. The key point: the program does not send a command every loop, only when the state changes. The code guarantees that like this:

main.c — relay_set() 
static void relay_set(int relay, int enabled)
{
    u8 command;

    if (relay < 0 || relay >= RELAY_COUNT) return;

    /* Nothing to do if the state is already the same.
       Without this, hundreds of USB packets per second would go out. */
    if (relay_state[relay] == (enabled ? 1 : 0)) return;

    relay_state[relay] = enabled ? 1 : 0;
    command = enabled ? relay_on_command[relay] : relay_off_command[relay];

    relay_send_command(command);
    show_relay_event(relay, enabled, command);
}

In addition, if the controller is unplugged or the link breaks, relays_all_off() is called. This is a safety behaviour: no relay should stay energised when the controller is gone.

4. Sending data over USB — the simplest form

Strip away the rest of the project (menus, password, memory card) and sending data from a PS2 to a USB HID device is really three steps.

Step 1 — Recognise the device (probe)

For every new USB device, usbd.irx calls your driver's probe function and asks "is this device yours?". Return 1 and the device is yours.

iop/seda_relay_irx.c — simplified 
static int seda_probe(int dev_id)
{
    UsbDeviceDescriptor *dev;

    /* Read the device's identity card */
    dev = sceUsbdScanStaticDescriptor(dev_id, NULL, USB_DT_DEVICE);
    if (!dev) return 0;

    /* Is this the device I am looking for? */
    if (dev->idVendor != target_vid || dev->idProduct != target_pid)
        return 0;

    return 1;   /* yes, it is mine */
}

Step 2 — Connect and open a "pipe"

On USB, data flows through channels called endpoints. To write to an endpoint you first need a handle from sceUsbdOpenPipe.

iop/seda_relay_irx.c — simplified 
static int seda_connect(int dev_id)
{
    UsbConfigDescriptor    *conf;
    UsbInterfaceDescriptor *intf;
    UsbEndpointDescriptor  *out_ep;

    conf = sceUsbdScanStaticDescriptor(dev_id, dev, USB_DT_CONFIG);
    intf = find_hid_interface(dev_id, conf);        /* find the HID interface */

    /* Control pipe: every USB device has one, endpoint 0.
       A NULL second argument means "endpoint 0". */
    relay_dev.control_ep = sceUsbdOpenPipe(dev_id, NULL);

    /* Interrupt OUT pipe: if present, this is the one we actually use */
    out_ep = find_interrupt_out_endpoint(intf, conf);
    if (out_ep)
        relay_dev.interrupt_out_ep = sceUsbdOpenPipe(dev_id, out_ep);

    /* Configure the device (SET_CONFIGURATION) */
    sceUsbdSetConfiguration(relay_dev.control_ep,
                            conf->bConfigurationValue,
                            config_done, &relay_dev);
    return 0;
}

Step 3 — Send the packet

This is the heart of it. Prepare 8 bytes, write them to the pipe, wait for the result:

iop/seda_relay_irx.c — the essence 
/* 1) Prepare the packet */
memset(relay_dev.report, 0, sizeof(relay_dev.report));
relay_dev.report[0] = 0x01;          /* fixed header */
relay_dev.report[3] = (u8)command;   /* 1..4 = ON, 17..20 = OFF */

/* 2) Send — this call returns IMMEDIATELY, the job is not finished yet */
start_result = sceUsbdInterruptTransfer(
    relay_dev.interrupt_out_ep,   /* which pipe          */
    relay_dev.report,             /* data                */
    8,                            /* how many bytes      */
    transfer_done,                /* function called when done */
    &relay_dev);                  /* data passed to the callback */

/* 3) Wait for completion */
result = wait_transfer_result(start_result);

The most important concept: USB transfers are asynchronous. sceUsbdInterruptTransfer does not mean "send", it means "queue the send" and returns at once. When the data has really gone out, usbd.irx calls the callback you supplied. That is why the code has a semaphore (done_sema):

iop/seda_relay_irx.c — waiting mechanism 
/* usbd.irx calls THIS when the transfer completes */
static void transfer_done(int result, int bytes, void *arg)
{
    relay_dev.transfer_result = result;
    relay_dev.transfer_bytes  = bytes;
    SignalSema(done_sema);        /* raise the "done" flag */
}

/* We wait for the flag — at most 3 seconds */
static int wait_transfer_result(int start_result)
{
    int i;
    if (start_result != USB_RC_OK) return start_result;

    for (i = 0; i < 300; i++) {
        if (PollSema(done_sema) == 0)      /* flag raised? */
            return relay_dev.transfer_result;
        DelayThread(10000);                /* sleep 10 ms, look again */
    }

    relay_dev.transfer_result = -1000;     /* timeout */
    return relay_dev.transfer_result;
}

Interrupt transfer or control transfer?

Interrupt OUTControl (SET_REPORT)
Pipe usedThe device's interrupt OUT endpointEndpoint 0 (present on every device)
FunctionsceUsbdInterruptTransfersceUsbdControlTransfer
RequirementDevice must have an OUT endpointAlways works
Speed / efficiencyBetterSlower, extra overhead
In this projectDefault pathFallback path

The code supports both, because some HID devices have no interrupt OUT endpoint at all — then the only option is a SET_REPORT request over the control pipe. The code detects this inside seda_connect and notes it.

5. How the EE talks to the IOP (SIF RPC)

Between the two processors there is a hardware bridge called the SIF. Over it you perform remote procedure calls (RPC): the EE fills a structure and sends it, the IOP processes it and sends the same structure back. Just like a network request, but between two chips.

The definitions both sides need are collected in a single header:

seda_relay_rpc.h — included by both sides 
#define SEDA_RELAY_RPC_ID 0x5344524c   /* "SDRL" — the service's address */

#define SEDA_RELAY_RPC_SEND_COMMAND 1
#define SEDA_RELAY_RPC_GET_STATUS   2

typedef struct {
    int result;            /* filled by IOP: operation result */
    int command;           /* filled by EE:  1..20            */
    int mode;              /* filled by EE:  send mode        */
    int status;            /* filled by IOP: connected?       */
    int control_result;    /* diagnostics                     */
    int interrupt_result;  /* diagnostics                     */
} SedaRelayRpcPacket;

The IOP side registers the service and waits for requests in an endless loop:

static void rpc_thread(void *arg)
{
    sceSifInitRpc(0);
    sceSifSetRpcQueue(&rpc_queue, GetThreadId());
    sceSifRegisterRpc(&rpc_server, SEDA_RELAY_RPC_ID,
                      rpc_handler, &rpc_buffer, NULL, NULL, &rpc_queue);
    sceSifRpcLoop(&rpc_queue);      /* never returns */
}

The EE side first finds the service (bind), then calls it:

/* Once: find the service */
SifBindRpc(&relay_rpc, SEDA_RELAY_RPC_ID, 0);

/* For every command: call */
relay_rpc_packet.command = command;
relay_rpc_packet.mode    = usb_send_mode;

SifCallRpc(&relay_rpc,
           SEDA_RELAY_RPC_SEND_COMMAND,
           0,                                  /* 0 = wait until finished */
           &relay_rpc_packet, sizeof(...),     /* sent     */
           &relay_rpc_packet, sizeof(...),     /* returned */
           NULL, NULL);

Why __attribute__((aligned(64)))? The SIF bridge works with DMA, and DMA requires the data to be aligned to a certain boundary in memory. Forget the alignment and the data gets corrupted or never arrives — and you get no error message. That is why every buffer carried over RPC is declared aligned. For the same reason pad_buf is 64-byte aligned.

Binding has one more subtlety: right after the IRX is loaded, the RPC service may not be ready yet. That is why bind_relay_rpc() tries 120 times with nopdelay() pauses in between.

6. The relay board protocol and the "12 modes" story

The board's manufacturer never published the protocol. The only reference was a C# program that works on Windows — windows-test/SedaRelayHid.cs: 

byte[] outputBuffer = new byte[9];
outputBuffer[0] = 0;          /* report ID */
outputBuffer[1] = 1;
outputBuffer[4] = command;
writeRawReportToDevice(outputBuffer);

The problem: the Windows HID driver interprets the first byte of the buffer as the report ID and handles that byte itself on the way to the cable. So what really goes over the wire differs from the array the application sees. On the PS2, you write the raw packet yourself. Because of this uncertainty the code contains two packet layouts and a total of 12 send modes: 

/* Layout A — exact copy of the Windows buffer */
static void fill_seda_report(int command, int command_index)
{
    memset(relay_dev.report, 0, sizeof(relay_dev.report));
    relay_dev.report[0] = 0x00;
    relay_dev.report[1] = 0x01;
    relay_dev.report[command_index] = (u8)command;   /* usually index 4 */
}

/* Layout B — report ID stripped; THIS IS THE ONE THAT WORKS */
static void fill_seda_payload_report(int command)
{
    memset(relay_dev.report, 0, sizeof(relay_dev.report));
    relay_dev.report[0] = 0x01;
    relay_dev.report[3] = (u8)command;
}

Layout B is Layout A shifted one byte to the left — exactly the difference explained by Windows swallowing the report ID. The default mode is therefore SEDA_RELAY_MODE_INT_PAYLOAD8 (mode 9): 8-byte interrupt OUT, no report ID.

The other 11 modes are diagnostic tools. You can switch modes from the settings screen and try which one sticks. MODE_AUTO (mode 0) brute-forces: it tries length × report type × recipient combinations in turn and uses the first one that works. That loop is at the end of seda_send_command.

General lesson: when working with an undocumented USB device you will not find the right packet on the first try. Building "a trial mechanism with adjustable parameters" into the code — and making it adjustable from the device's own screen — is far faster than recompiling and rewriting the disc every time. The mode system and the VID/PID editing screen in this project exist exactly for that reason.

7. Wiring and electrical notes

The Seda Elektronik board uses two USB connections: one is the board's 5 V power supply, the other is the HID data link. Both go to the two USB ports of the PS2 Slim. The actual motor power is on the board's relay contact side; it does not come from the PS2's USB line.

PS2 USB port 1 ---- 5 V power USB ----+ PS2 USB port 2 ---- HID data USB -----+---- [ Seda 8-channel relay board ] | 3S LiPo (+) ---- NO1..NO4 | first four relays 3S LiPo (-) ---- NC1..NC4 | v [COM1, COM2] ---- the two terminals of the paralleled left RS-540 motors [COM3, COM4] ---- the two terminals of the paralleled right RS-540 motors One relay ON in a group: motor runs Both relays OFF: both terminals (-), motor stops Both relays ON: both terminals (+), motor stops

A relay has three terminals and the logic is:

TerminalMeaningRelay idleRelay energised
COMCommonAlways in circuit
NONormally openDisconnectedConnected to COM
NCNormally closedConnected to COMDisconnected

In this vehicle's bidirectional wiring all NC terminals are on the LiPo (−) rail and all NO terminals on the LiPo (+) rail. COM1–COM2 go to the left motor group's terminals, COM3–COM4 to the right group's. Therefore both relays of one group being ON at the same time is not a supply short circuit; it puts (+) on both motor terminals and simply stops the motor.

Current warning — skip this and you burn hardware.

  • The Seda board's separate 5 V power USB is on one PS2 USB port; the HID data cable is on the second port. Measure the board's rated current draw and the 5 V on the PS2 port under load.
  • There must be a driver between the coil and the microcontroller: ULN2003/ULN2803 or a transistor. Preferably galvanic isolation with an optocoupler.
  • A freewheel (snubber) diode across every coil — the reverse spike when the coil releases kills the driver transistor. Ready-made boards usually have it, but do not forget it if you build your own.
  • Do not confuse the coil diode with motor suppression. Because the motor polarity is reversed, a unidirectional 1N5408 must not go across the motor terminals; a bidirectional TVS or a suitable RC snubber is needed.
  • If you switch mains voltage (220 V), mind the clearance between the low-voltage and high-voltage areas of the board.

A few interesting spots in main.c

  • Screen output: log_printf() prints the same text both with printf (emulator/ps2client console) and scr_vprintf (TV screen). Very handy for diagnostics.
  • Settings file: mc0:SYS-CONF/ROLECFG.TXT — plain text lines such as mode=9 / vid=178E. Text was chosen over a binary format so it can be edited by hand.
  • Password screen: a 12-button sequence (XXX □□□ △△△ ○○○) to enter settings. The purpose is not security but preventing the user from breaking settings by accident.
  • Button edge detection: current_buttons = 0xffff ^ buttons.btns; — PS2 controller buttons arrive with inverted logic (pressed = 0). XOR corrects it. Then pressed = current & ~previous finds "newly pressed" and released = previous & ~current finds "newly released".

9. Building and running

Build order matters, because the EE side embeds the IOP side's output:

iop/seda_relay_irx.c --compile--> iop/seda_relay.irx | convert to C array with bin2c v seda_relay_irx.c | $(PS2SDK)/iop/irx/usbd.irx --bin2c--> usbd_irx.c | main.c + usbd_irx.c + seda_relay_irx.c -----+--> relay.elf | role.elf (copy, --strip-debug) | disc/ROLE.ELF + SYSTEM.CNF | role-disc.iso

In practice, a single command:

powershell -ExecutionPolicy Bypass -File build-disc.ps1

This script first calls build.ps1 (sets the PS2SDK paths, runs make clean + make), then produces the ISO with MSYS2's xorriso. If you only need the ELF, running build.ps1 alone is enough.

relay.elf keeps the developer debug information. role.elf, the file that is copied to the memory card, is automatically passed through --strip-debug while keeping the same entry address and the same LOAD segment. The distribution file is therefore much smaller; always use role.elf when transferring to the PS2.

Emulator limit: with PCSX2 you can test the controller, screen, menu and memory card parts of the program — the logs show them loading. But real USB device pass-through is not reliable in the emulator. The relay protocol can only be verified on a real console. That is why the result / status / ctrl / int numbers on the screen matter: they are the only way to debug by looking at the TV.

10. Motion programming mode

During normal driving the START button opens recording mode and, for safety, immediately switches every relay off. In this mode the motion buttons do not run the motors; they are recorded into a RAM array of up to 128 steps. Cross, Circle, Triangle and Square are driving moves; R1 adds a one-second wait step with all relays off.

A second START executes the recording. Each entry lasts one second. If the same move repeats consecutively the relay is not released in between; e.g. X, X drives forward for two uninterrupted seconds. At the end of every different move all relays are switched off and the next move is applied. When the program finishes, the recording is cleared and the relays stay off.

SELECT cancels the program while recording; during execution it is polled every 10 ms and acts as an emergency stop. In both cases all relays are switched off. The R1 settings-screen behaviour in normal mode is preserved. START+SELECT still returns to the PS2 main menu.

Safe shutdown: the software does not use the bulk 0xFC command, which was never verified on the board. Every full shutdown sends the individually verified 17, 18, 19, 20 OFF commands. If an OFF command cannot be verified, the program does not energise the next direction. Program transitions, the SELECT emergency stop and controller disconnection all use the same safe shutdown path.

10.1 Relay dead time

When switching from one direction to the opposite, the relay contacts must not be closed at the same time. So in live driving, the moment a relay is switched off the software completes all switch-offs and then applies a configurable wait; only after that may the opposite relay be switched on. During program execution the wait is applied immediately before energising the next relay. The default is 100 ms; it is changed on the settings screen's Dead time line with LEFT/RIGHT in 10 ms steps between 0 and 1000 ms, and saved to the memory card under the deadms= key.

The wait is applied only when it is actually owed:

  • When an energised relay is released in live driving; this includes releasing one of Cross and Triangle after briefly holding both.
  • On the first energisation after relays_all_off() — during program execution every step transition takes this path.

Because in live driving the wait completes while the relay is opening, an independent press made later gets no extra delay. In program execution every distinct move step is 1 s on + 100 ms dead time; a six-step program takes about 6.5 s.

10.2 Saving the program to the memory card and recalling it with one button

In recording (programming) mode:

  • L1 — writes the current sequence to the memory card.
  • L2 — loads the saved sequence from the card back into RAM (you can append to it and save again).

On the normal driving screen, L2 reads the saved program from the card with one button and runs it immediately. If the card is empty or the file is corrupt it shows a warning and touches no relay.

The file is plain text at mc0:SYS-CONF/ROLEPRG.TXT:

ROLEPRG v1
steps=XXOTSW

Letters: X = Cross, O = Circle, T = Triangle, S = Square, W = wait. The reader also accepts lower case, commas and spaces; if it sees an unknown letter it rejects the file and leaves the current sequence untouched. At most 128 steps are read.

Summary: what to remember

  1. On the PS2, the IOP, not the EE, accesses USB. That is the only reason the project is split in two.
  2. The two sides talk over SIF RPC; the structure carried is defined in seda_relay_rpc.h and must be aligned because of DMA.
  3. Sending data over USB is essentially three steps: probe (is this device mine) → openPipe (open a pipe) → transfer (write and wait for the callback).
  4. USB transfers are asynchronous; the function returning does not mean the job is done.
  5. The board expects an 8-byte interrupt OUT packet: byte[0]=0x01, byte[3]=command.
  6. Relay coils are not powered from USB; a separate supply + driver + freewheel diode are mandatory.
  7. A new HID device (e.g. a board you build with a PIC18F4550 or PIC16F1455) that implements the same packet format works on the PS2 side without changing a single line of code — just enter the VID/PID on the settings screen.
