PS2 Robot Vehicle — Phase Plan

Goal: take a mains-powered PS2 Slim with FreeMCBoot off the wall socket with a battery and turn it into a 4-wheel robot vehicle, wirelessly controlled from a PC, with an EyeToy camera. The relay board and its software already work — this plan builds on top of them.

The plan's single rule: at the end of every phase there must be something that works. The phases are cut this way so you never spend months on a pile where nothing runs. Even if Phase 3 gets stuck, you are left with a drivable vehicle.

Phases

PHASE 1

Make it drive

Easy · No code

When done: a 4-wheel car that runs on a battery and that you drive with a DualShock.

This phase is entirely electrical and chassis work. The existing role.elf is used as is.

Power architecture

[3S LiPo]---[buck 8.5V]---> PS2 Slim | [Motor LiPo]---[motor driver]---> motors | GNDs join here (GND ONLY)

The most critical decision: the PS2 and the motors are fed from separate battery packs.

Motors draw high current at start-up and when reversing, and the supply voltage dips for an instant. If they share the same pack, the PS2 resets at the start of every move. This single decision determines whether the project works at all.

Note: the later Phase 1 electronics document (PHASE1_ELECTRONICS.html) refines this — with a wide-margin buck and a 12.8 V LiFePO4 pack, one battery with two fused branches is sufficient.

  • Look at the PS2 adapter label (typically 8.5 V on the Slim) — set the buck converter accordingly
  • Choose the buck with plenty of margin: at least twice the current the PS2 draws
  • Low-voltage protection is mandatory — a LiPo cell below 3.0 V is permanently dead
  • Rough estimate: a 3S 5000 mAh (~55 Wh) pack at 15–25 W consumption gives around 2 hours

Motor wiring (with the existing relay board)

RelayRoleButton
1Left motor forwardCross
2Left motor reverseSquare
3Right motor forwardTriangle
4Right motor reverseCircle

Tank-style turning: one side forward, the other reverse. The board has 8 channels, 4 are spare — keep them for lights/horn.

Know the limit: a relay has no speed control, it is either full throttle or stop. Relays are mechanical; click them several times a second and the contacts wear. Speed control is not a Phase 1 topic.

(The final button mapping and the bidirectional SPDT wiring actually built are documented in PROJECT_GUIDE.html, section 1 and 7.)

PHASE 2

Wireless control

Medium

When done: a vehicle you drive from the PC with keyboard/gamepad. No controller cable.

Hardware

The PS2 Slim already has an Ethernet port (on the back, built-in SMAP/DEV9 hardware). To make it wireless, a small WiFi bridge rides on the vehicle — a mini router in client/bridge mode. The PS2 thinks it is connected by cable.

PS2 [Ethernet] ---cable--- [WiFi bridge] ))) WiFi ((( [PC] (on the vehicle, powered from 5V)

This consumes no USB port — both USB ports stay free for the relay board and the EyeToy. Take the bridge's 5 V from the main battery through a small buck, not from the PS2's USB port.

Software

  • ps2ip.irx + ps2smap.irx are loaded (embedded in the ELF like usbd.irx)
  • A TCP listener is added next to the button-reading loop in main.c
  • The incoming byte is handed straight to the existing relay_send_command()
  • The IOP driver, the RPC layer and the packet format are not touched at all
  • The controller keeps working in parallel — if the network drops you can intervene by hand

Bonus: once the network works, uLaunchELF's built-in FTP server gives you access to mc0:, mass: etc. from the PC. Not extra work, a gift.

Add a safety behaviour: if the network connection drops, the motors must stop. If no command arrives for a certain time (e.g. 1 s), call relays_all_off(). Otherwise the vehicle keeps executing the last command when WiFi cuts out.

PHASE 3

Camera research

Unknown · Critical decision point

When done: you know whether Phase 4 will take weeks or months.

There is one question to answer before writing any code:

Is there a usable EyeToy driver on the PS2 homebrew side?

AnswerConsequence
Yes, it worksPhase 4 shrinks to a few weeks
Partially / outdatedAdaptation work, medium
NoDriver from scratch — the project's biggest item

EyeToy technical profile

VID / PID0x054C / 0x0154 or 0x0155 (two revisions)
ChipOmniVision OV519
Resolution320×240 @ 30 fps · 640×480 @ 15 fps
Transfer typeIsochronous (sceUsbdIsochronousTransfer)
ExtraBuilt-in microphone

The detail that saves the project: USB 1.1 bandwidth is 12 Mbps, while raw 320×240 video is ~4.6 MB/s — it does not fit. So the camera has to send the data compressed, and it does. The format is very close to JPEG, only the headers and quantisation tables are stripped.

Result: the PS2 does not need to decode the image. Prepend the right header and pass the bytes straight through over the network; the PC does the decoding. You are spared writing a JPEG decoder for a 36 MHz IOP.

This phase's deliverable: a descriptor dumper

Write a diagnostic tool, not a driver. Copy the probe skeleton from the relay driver, recognise the EyeToy and print every descriptor it sees to the screen: interfaces, endpoints, isochronous packet sizes, alternate settings.

~150 lines, low risk, and it tells you what you are really dealing with. The "try 12 modes and find the one that sticks" approach worked on the Seda board — the same habit applies here.

PHASE 4

Single frame

Hard · The heart of the project

When done: a single photo from the EyeToy on the PC screen. Not a stream, one frame.

Do not jump to streaming. Once a single frame works the hard part is over; the rest is repetition.

  1. Initialise the OV519 registers (resolution, format, frame rate)
  2. Receive packets from the isochronous endpoint
  3. Reassemble the packets into a full frame (find the frame boundaries)
  4. Add the JPEG header + quantisation table to make a valid file
  5. Move it to the EE over SIF RPC
  6. Send it to the PC over TCP

Do not write the photo to the memory card. 8 MB capacity, ~100–150 KB/s write speed, limited flash life — and FreeMCBoot lives on that card. If it gets corrupted the console will not boot. Let the image flow straight over the network; intermediate storage is a needless step.

PHASE 5

MJPEG stream

Medium · Easy if Phase 4 is done

When done: live video in the PC browser, without installing extra software.

Send the frames back to back as MJPEG over HTTP. The method IP cameras have used for decades — the browser shows it without any plug-in: 

<img src="http://192.168.1.50:8080/stream">
EyeToy --iso--> IOP --SIF--> EE --TCP--> WiFi bridge --> browser (compressed) (header added) (MJPEG)

Realistic ceiling

ExpectationWhy
Resolution320×240USB 1.1 bandwidth + IOP capacity
Frame rate10–15 fpsNetwork stack and SIF transfer
Latency200–500 msBridge + ps2ip + browser buffering

You cannot drive a vehicle with half a second of latency — you will hit the wall. Do not design the vehicle as "drive by watching live video". Build a "move → stop → look → move again" model, or add a distance sensor and give the PS2 a self-stop reflex.

Next step: consolidating onto one USB port

Phases 1–2 run with the existing relay board. But once the EyeToy takes the second port you cannot plug in anything else, and a USB hub is not to be relied on (usbd.irx's hub support is unreliable and it eats the power budget).

The permanent solution: replace the relay board with your own HID microcontroller board (PIC18F4550 or PIC16F1455). Relays + motor PWM + distance sensor + battery voltage measurement all gather on one port, the second port stays for the EyeToy.

If the board implements the existing 8-byte packet format (byte[0]=0x01, byte[3]=command), not a single line changes on the PS2 side — entering the VID/PID on the settings screen is enough. That is why, in the robot project, this board is promoted from "would be nice" to "required".
