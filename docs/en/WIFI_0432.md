# 0.4.32 — hub monitoring after runtime faults

The owner reported sustained motor control with the relay connected directly,
but loss of relay response after a few operations through the black four-port
unpowered hub. On the running 0.4.31 console, both hub queries and relay USB
configuration reported PS2SDK error 5 (`USB_RC_NORESPONSE`). Cached descriptors
still listed the hub and relay; that does not prove either was responding.
Wi-Fi on the other root port and the gamepad thread remained active.

This release fixes two recovery gaps found during source inspection:

- Failed runtime hub/port/interrupt status requests previously returned without
  rearming monitoring. A per-hub timer now resumes discovery with 250 ms–4 s
  backoff and rescans all child ports after potentially lost notifications.
- A connected, disabled child port is re-enumerated individually. Other ports,
  active resets and overcurrent states are preserved. Whole-hub power is not
  cycled. Pending control/interrupt DMA requests are not reused or overwritten.
- Relay-only recovery no longer stops permanently after three attempts. It
  retains the existing polling interval and fault/output safeguards.
- Disconnect cancels the hub retry timer; private-structure changes explicitly
  rebuild all USBD objects to preserve consistent internal layouts.

The production recovery helper and actual USBD timer pass host tests covering
backoff, pending-request protection, child reset, overcurrent and unplug/stale
callbacks. Existing reset/port mapping, relay lifecycle, 552,928 protocol checks,
EE scheduler/renderer and native EE/IOP integration tests also pass.

Physical status: 0.4.32 was staged at `mc0:/Wifi/WIFI.ELF` and its 804,312-byte
size verified with HEAD only. No remote restart or motion commands were sent
during this investigation because motor-power isolation could not be tested.
A new session running an interim 0.4.32 image was observed during transfer;
activation of the final 804,312-byte image remains unverified and requires
reopening the ELF or the next console startup.

These changes address recovery after a transient error, not its electrical
origin. The unpowered hub's supply stability, relay-coil transients and
motor-load interference remain unmeasured. A motor-power-disconnected test and
comparison with the owner's properly powered hub are still needed. No claim of
physical hub stability under motor load is made for this release.

Reproduce the focused host test from `wifi/`:

```powershell
gcc -std=c99 -O2 -Itests -Iinclude tests/usbd_hub_runtime.c -o reports/usbd_hub_runtime.exe
reports/usbd_hub_runtime.exe
```
